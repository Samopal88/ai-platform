# TASK_PROMPT_TEMPLATES
## AI Workspace Platform

---

# 1. Назначение документа

Документ содержит шаблоны задач, которые GPT-5.4 использует для постановки подзадач Claude Code.

Цель шаблонов:

- стандартизировать взаимодействие
- не давать Claude слишком широкие задачи
- получать предсказуемый результат
- сократить хаос при разработке
- упростить контроль качества

---

# 2. Общие правила для всех шаблонов

Каждый prompt для Claude Code должен:

- содержать режим работы
- содержать путь к проекту
- содержать чёткую цель
- содержать ограничения
- содержать формат ожидаемого ответа
- запрещать лишние действия

Общие ограничения по умолчанию:

- не менять `.env`
- не менять секреты
- не делать deploy
- не делать `git push`
- не удалять файлы без явного разрешения
- не выходить за рамки задачи
- не делать широкие рефакторинги без необходимости

# 3. Универсальный шаблон

```text
Режим: {MODE}
Проект: {PROJECT_PATH}

Контекст:
{CONTEXT}

Цель:
{TASK_DESCRIPTION}

Ограничения:
- Не выходить за рамки задачи
- Не делать широких рефакторингов
- Не менять .env
- Не менять секреты
- Не выполнять deploy
- Не делать git push
- Не удалять файлы без прямого указания
- Не устанавливать сторонний софт без прямого указания

Нужно вернуть:
1. Что сделано
2. Какие файлы затронуты
3. Какие команды запускались
4. Какие проблемы найдены
5. Какие риски замечены
6. Следующий рекомендуемый шаг
```

---

# 4. Шаблон INVESTIGATE

Используется, когда нужно только исследование.

```text
Режим: INVESTIGATE
Проект: {PROJECT_PATH}

Цель:
Исследуй проблему: {PROBLEM_DESCRIPTION}

Ограничения:
- Ничего не меняй
- Не редактируй файлы
- Не выполняй deploy
- Не меняй конфиги
- Не меняй .env
- Не делай широких выводов без подтверждения

Нужно вернуть:
1. Предполагаемую причину
2. Какие файлы относятся к проблеме
3. Какие строки/фрагменты подтверждают вывод
4. Какие команды запускались
5. Что проверить следующим шагом
```

---

# 5. Шаблон PLAN

Используется, когда нужно получить план реализации.

```text
Режим: PLAN
Проект: {PROJECT_PATH}

Цель:
Подготовь план для задачи: {TASK_DESCRIPTION}

Контекст:
{CONTEXT}

Ограничения:
- Ничего не меняй
- Не создавай файлы
- Не редактируй код
- Не предлагай переписывать проект полностью
- Предлагай только реалистичные шаги для текущего MVP

Нужно вернуть:
1. Пошаговый план
2. Какие файлы нужно создать или изменить
3. Какие риски есть
4. Что лучше сделать сначала
5. Что можно отложить
```

---

# 6. Шаблон PATCH

Используется, когда задача уже одобрена и нужно внести изменение.

```text
Режим: PATCH
Проект: {PROJECT_PATH}

Цель:
Реализуй задачу: {TASK_DESCRIPTION}

Контекст:
{CONTEXT}

Ограничения:
- Меняй только необходимые файлы
- Не делай широкий рефакторинг
- Не меняй .env
- Не меняй секреты
- Не выполняй deploy
- Не трогай unrelated code
- Соблюдай текущую архитектуру проекта

Нужно вернуть:
1. Что изменено
2. Какие файлы изменены
3. Краткое объяснение решения
4. Какие команды проверки запускались
5. Есть ли незавершённые места
6. Следующий рекомендуемый шаг
```

---

# 7. Шаблон VERIFY

Используется после внесения изменений.

```text
Режим: VERIFY
Проект: {PROJECT_PATH}

Цель:
Проверь, корректно ли работает реализация задачи: {TASK_DESCRIPTION}

Ограничения:
- Не вноси новых изменений без крайней необходимости
- Не расширяй scope
- Не переделывай решение заново
- Только проверка, тесты и вывод

Нужно вернуть:
1. Какие проверки выполнены
2. Какие команды запускались
3. Результаты проверок
4. Есть ли ошибки
5. Что ещё осталось проверить
```

# 8. Шаблон CREATE_FILE

Для создания нового файла.

```text
Режим: PATCH
Проект: {PROJECT_PATH}

Цель:
Создай новый файл: {FILE_PATH}

Описание:
{FILE_PURPOSE}

Ограничения:
- Не меняй другие файлы без необходимости
- Не создавай лишние модули
- Следуй текущему стилю проекта

Нужно вернуть:
1. Что создано
2. Для чего файл нужен
3. Какие зависимости появились
4. Что нужно сделать следующим шагом
```

```text

Проект: {PROJECT_PATH}

Цель:
Внеси точечные изменения в файл: {FILE_PATH}

Что нужно сделать:

Ограничения:

- Не меняй поведение других частей системы без указания

Нужно вернуть:
1. Что изменено
2. Почему это изменено
3. Что может быть затронуто побочно
4. Какие проверки нужны
```

# 10. Шаблон DATABASE_STEP

Для работы с БД и миграциями.

```text
Режим: PATCH
Проект: {PROJECT_PATH}

Цель:
Реализуй изменение в БД: {DB_CHANGE_DESCRIPTION}

Ограничения:
- Не делай лишних изменений в моделях
- Не меняй unrelated tables
- Подготовь миграцию аккуратно
- Не применяй destructive changes без явного указания

Нужно вернуть:
1. Какие таблицы/модели затронуты
2. Какие поля добавлены/изменены
3. Какая миграция создана
4. Есть ли риски для данных
5. Какие проверки обязательны
```

# 11. Шаблон FRONTEND_STEP

Для интерфейсных задач.

```text
Режим: PATCH
Проект: {PROJECT_PATH}

Цель:
Реализуй UI-задачу: {UI_TASK_DESCRIPTION}

Контекст:

Ограничения:

4. Какие проверки UI стоит выполнить
```

# 12. Шаблон FILE_TOOL_TASK

Для редактирования файлов пользователя.

```text
Режим: PATCH
Проект: {PROJECT_PATH}

Цель:
Измени пользовательский файл: {FILE_NAME}

Задача:
{FILE_TASK_DESCRIPTION}

Тип файла:
{FILE_TYPE}

Ограничения:
- Сохрани структуру файла, если не указано иное
- Не повреждай формат
- Не удаляй данные без прямого указания
- Если включено версионирование — создай новую версию

Нужно вернуть:
1. Что изменено в файле
2. Какие листы/разделы/блоки затронуты
3. Как сохранить/скачать результат
4. Есть ли ограничения или риски
```

Для поиска информации в интернете.

```text
Режим: INVESTIGATE
Проект: {PROJECT_PATH}

Цель:
Найди информацию по теме: {RESEARCH_TOPIC}

Нужно вернуть:
1. Краткий вывод
2. Какие источники использованы
3. Что важно для проекта
4. Какие решения можно применить
```

# 14. Шаблон BUGFIX

Для исправления конкретной ошибки.

```text
Режим: PATCH
Проект: {PROJECT_PATH}

Цель:
Исправь баг: {BUG_DESCRIPTION}

Контекст:
{CONTEXT}

Ограничения:
- Не делай рефакторинг вне причины бага
- Сначала найди источник проблемы
- Меняй только связанные части
- После исправления запусти проверки

Нужно вернуть:
1. Причину бага
2. Что изменено
3. Какие проверки выполнены
4. Исправлен ли баг
5. Что стоит проверить вручную
```

---

# 15. Шаблон SAFE_STOP

Используется, когда GPT хочет остановить Claude и зафиксировать промежуточный результат.

```text
Режим: VERIFY
Проект: {PROJECT_PATH}

Цель:
Остановись на текущем состоянии и зафиксируй промежуточный результат по задаче: {TASK_DESCRIPTION}

Нужно вернуть:
1. Что уже готово
2. Что ещё не готово
3. Какие файлы изменены
4. Что нужно доделать следующим шагом
5. Есть ли риски продолжения без approve
```

---

# 16. Правила выбора шаблона

- Если нужно понять проблему → INVESTIGATE
- Если нужен план → PLAN
- Если нужно внести изменение → PATCH
- Если нужно проверить результат → VERIFY
- Если нужно точечно исправить баг → BUGFIX
- Если нужно изменить пользовательский файл → FILE_TOOL_TASK
- Если нужен поиск в интернете → WEB_RESEARCH

Оркестратор GPT-5.4 должен использовать эти шаблоны как обязательную основу постановки задач Claude Code.

- предсказуемость
- управляемость
- прозрачность
- снижение хаоса
- защиту от бессмысленного кода
